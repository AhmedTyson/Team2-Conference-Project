📄 الملف الأول: Tasks_plan.md — الخطة المعمارية

الملف ده هو الاستراتيجية الأساسية بتاعة الموديول الجديد اسمه "User Interactions (Community)" — يعني فايتوري المفضلة والمراجعات. وهنا الفكرة الأساسية كلها مبنية على إننا هنشتغل مع APIs خارجية (RapidAPI للفنادق والمطاعم + OpenFlights للطيران).

🎯 المشكلة اللي بنحلها

العلاقات بتاعت Laravel (زي المفضلة والمراجعات) شغالة على ID محلي في الداتابيز بتاعنا. بس المشكلة إن البحث عن الفنادق والطيران بييجي من APIs خارجية — يعني الكيانات دي مش موجودة في الداتابيز بتاعنا أصلًا. فإزاي نعلّق عليهم مفضلة أو مراجعة؟

💡 الحل: "Shadow Modeling" — النمذجة الظلية

الفكرة: بدل ما نعمل ETL (نسخ الداتابيز العالمية كلها — بطيء ومش محتاجينه) أو نجيب الداتا على طول كل مرة (يسبب N+1 مشاكل في الأداء) → هنعمل الآتي:
  • البحث/العرض: بيحصل عبر الـ APIs الخارجية، مع Cache قوي.
  • التفاعل (مفضلة/مراجعة): لما المستخدم يعمل تفاعل مع كيان خارجي، النظام بيعترض الطلب.
  • إنشاء الظل: الخدمة بتشوف لو الـ ID موجود محليًا. لو مش موجود → بتيجيبه من الـ API مرة واحدة وبتخزّنه في جدول محلي (سجل "ظل").
  • العلاقة المحلية: المفضلة أو المراجعة بتتلحق بالسجل الظلي ده بالعلاقات العادية morphMany و morphedByMany.

✅ فوائد الحل

  • علاقات Eloquent عادية بتشتغل من غير أي تعديل.
  • صفر N+1 HTTP calls لما نجيب ملف المستخدم أو مفضلاته.
  • داتابيز خفيف — بنخزن بس الكيانات اللي المستخدم تفاعل معاها.
  • مقاومة الأعطال — لو الـ API الخارجي وقع، المستخدم لسه شايف مفضلاته ومراجعاته.

🏗️ الطبقات المعمارية (N-Tier) للـ APIs الخارجية

  • طبقة 1 — API Clients (app\Infrastructure\External\): كلاسات مخصصة للتكامل، زي RapidApiHotelClient، مع Http::retry() و timeouts للمقاومة.
  • طبقة 2 — DTOs (app\DTOs\): بتوحيد رد الـ API في كائنات منضبطة زي HotelDTO.
  • طبقة 3 — Services (app\Services\): HotelService::resolveEntity($externalId) — ده اللي بينفّذ منطق الـ Shadow Modeling (دور محلي → ولا هات خارجي → احفظ محلي → ارجع محلي).
  • طبقة 4 — Interactors (app\Services\InteractionService): بيدير منطق إضافة/إزالة المفضلات والمراجعات.

المرحلة الأولى: أساس الداتابيز

تاسك 1: تحديث سكيما الدومينز لـ Shadow Modeling الحجم: صغير

هنضيف أعمدة للجداول hotels و restaurants و flights عشان نقدر نخزّن الكيانات الخارجية محليًا.

شروط القبول:
  • إضافة external_id (نص، مفهرس) للجداول الثلاثة.
  • إضافة provider (نص) — مثال: 'rapidapi' أو 'openflights'.
  • خلّي الأعمدة غير الأساسية nullable، لأن سجل الظل محتاج بس الداتا الأساسية للعرض.
  • إضافة unique constraint على الثنائي (provider, external_id).
ملفات: xxxx_create_hotels_table.phpxxxx_create_restaurants_table.phpxxxx_create_flights_table.php
تاسك 2: إنشاء جداول المفضلات والمراجعات الحجم: صغير

جداول polymorphic للمفضلة والمراجعة بتاعة المستخدم.

شروط القبول:
  • إنشاء جدول favourites بأعمدة: user_id, favouritable_type, favouritable_id.
  • إنشاء جدول reviews بأعمدة: user_id, reviewable_type, reviewable_id, rating, comment, status (pending/approved).
  • إضافة Foreign Key على user_id.
ملفات: xxxx_create_favourites_table.phpxxxx_create_reviews_table.phpapp/Models/Favourite.phpapp/Models/Review.phpapp/Models/User.php

المرحلة التانية: عملاء الـ APIs الخارجية

تاسك 3: تنفيذ External API Clients الحجم: متوسط

كلاسات HTTP متينة لـ RapidAPI (فنادق/مطاعم) و OpenFlights.

شروط القبول:
  • إنشاء RapidApiHotelClient فيه getById($externalId).
  • إنشاء RapidApiRestaurantClient فيه getById($externalId).
  • استخدام Http::withHeaders() لحقن مفاتيح الـ API من .env.
  • إضافة timeout و retry — مثال: Http::timeout(10)->retry(3, 100).
  • إلقاء custom exceptions عند فشل الـ API.
ملفات: app/Infrastructure/External/RapidApiHotelClient.phpapp/Infrastructure/External/RapidApiRestaurantClient.php

المرحلة التالتة: Shadow Modeling ومنطق العمل

تاسك 4: تنفيذ Shadow Resolution في الـ Services الحجم: متوسط

المنطق اللي بيدور على الكيان في الداتابيز، ولو مش موجود بيجيبه من الـ API وبيخزّنه.

شروط القبول:
  • تحديث HotelService بدالة resolveEntity($externalId): بيعمل Hotel::where('external_id', $externalId)->first().
  • لو مش موجود → استخدم RapidApiHotelClient->getById()، رتّب الداتا، واعمل Hotel::create().
  • كرر نفس النمط في RestaurantService.
ملفات: app/Services/HotelService.phpapp/Services/RestaurantService.php
تاسك 5: تنفيذ Interaction Services الحجم: متوسط

المنطق الأساسي لشغل المفضلات والمراجعات.

شروط القبول:
  • إنشاء InteractionService.
  • دالة toggleFavourite(User, type, externalId): تحلّ الـ shadow model وبعدين توجّل العلاقة الـ polymorphic.
  • دالة addReview(User, type, externalId, data): تحلّ الـ shadow model وتعمل مراجعة pending.
  • دالة deleteReview(User, reviewId): تتأكد إن المستخدم هو مالك المراجعة قبل الحذف.
ملفات: app/Services/InteractionService.php
