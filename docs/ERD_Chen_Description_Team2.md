# Smart AI Travel Planner — ERD Architecture & Rationale (Team 2 Guidance)
**Project:** ThreeDOS — Backend Development Council

This document provides the "4 Ws" (What, Who, When, Why) for the database architecture. It explains the reasoning behind the entities, their visual attributes (images), and their relationships to help developers and stakeholders understand the structural decisions.

---

## 1. User & Identity Module

### USER
* **What:** The core identity and authentication record. Holds credentials and visual identity (`profile_image`).
* **Who:** Both travelers (customers) and administrators.
* **When:** Created upon registration. Updated when users edit their profile.
* **Why:** Necessary for session management, RBAC (Role-Based Access Control), and tying data (trips, reviews, favorites) to a specific person. The `profile_image` was explicitly added so reviews and dashboards feel personalized and modern.

### ROLE & PERMISSIONS (via Spatie)
* **What:** Defines system permissions (e.g., `Admin`, `Customer`).
* **Why:** Instead of building a custom `ROLE` entity from scratch, the system delegates this entirely to the `spatie/laravel-permission` package. The package automatically generates and manages the `roles`, `permissions`, and `model_has_roles` pivot tables to handle dynamic RBAC out-of-the-box.

### SURVEY
* **What:** An onboarding preference profile (`travel_style`, `budget_level`, `interests`).
* **When:** Filled out right after registration or before creating the first trip.
* **Why:** By storing this in a 1:1 relationship with the USER, the AI Travel Planner can automatically inject the user's permanent preferences into the OpenAI prompt without forcing the user to select their interests every single time they plan a new trip.

## 2. Travel Planning Module

### TRIP
* **What:** The central container for a planned vacation. Holds user inputs (budget, duration) and visual state (`cover_image`).
* **Who:** Created by the User.
* **Why:** Groups all itinerary items and AI recommendations into a single manageable unit. The `cover_image` was added to ensure the user's "Saved Trips" dashboard looks like a modern travel grid (similar to Airbnb or Pinterest).

### ITINERARY_ITEM
* **What:** A single, chronological activity (e.g., "10:00 AM - Visit Eiffel Tower").
* **When:** Generated by the AI or manually added by the user after a trip is created.
* **Why:** Replaces complex M:N pivot tables. Flattening the daily schedule into a simple `belongs_to` Trip relationship makes it incredibly fast to query and render the day-by-day timeline on the frontend.

### TRIP_DESTINATION
* **What:** An associative entity (M:N pivot) connecting `TRIP` and `DESTINATION`.
* **Why:** A trip can span multiple cities (e.g., a Eurotrip covering Paris and Rome). This pivot stores metadata about *when* the user is in a specific destination (`day_number`, `visit_order`, `estimated_date`, `notes`) without duplicating the core destination data.

### AI_RECOMMENDATION
* **What:** A caching table storing the exact prompt sent to OpenAI and the raw response.
* **Why:** **Cost & Performance Control.** OpenAI charges per token and takes seconds to respond. By saving the generated recommendation, if a user re-opens their trip, the data loads instantly from our database rather than hitting the paid API again.

## 3. Geography & Destinations Module

### COUNTRY
* **What:** Top-level geographic boundary. Includes `flag_url` and `languages`.
* **When:** Synced/seeded via the external RestCountries API.
* **Why:** Required to group destinations and provide localized data (currency, flag) without duplicating that data on every single city.

### DESTINATION
* **What:** A specific city or travel hub (e.g., "Paris", "Kyoto"). Includes a primary `image`.
* **Who:** Managed by Admins via the CRUD dashboard.
* **Why:** Acts as the parent container for all local places (Hotels, Restaurants, Attractions). The `image` attribute ensures destination browsing cards are visually rich.

## 4. Local Places Module

### HOTEL, RESTAURANT, ATTRACTION, FLIGHT
* **What:** Distinct point-of-interest and booking entities. Every single place includes an `image` attribute.
* **Why separate entities?** While they seem similar, their business logic diverges significantly:
  * `HOTEL` requires pricing, stars, and availability.
  * `RESTAURANT` requires cuisine type and price range metrics.
  * `ATTRACTION` requires general descriptions and coordinates.
  * `FLIGHT` requires departure/arrival airports, dates, and pricing.
  Keeping them separate avoids a massive, sparse "Bookings" table full of NULL values and perfectly maps to the Admin Dashboard's distinct management tabs.

### CATEGORY
* **What:** Taxonomy tags for Attractions and Restaurants (e.g., "Beaches", "Museums", "Fine Dining"). Includes an `icon`.
* **Why:** Allows users to filter places dynamically. The `icon` attribute allows the frontend to render intuitive UI filter pills (e.g., a 🏖️ icon for Beaches) rather than just plain text.

## 5. User Interaction Module

### REVIEW
* **What:** A user's rating (1-5) and text feedback for a place.
* **Who:** Written by Users, moderated by Admins.
* **Why:** Modeled as a polymorphic relationship (`rates`) connecting to Hotels, Restaurants, Attractions, and Destinations. This prevents creating 4 separate identical review tables, keeping the database DRY (Don't Repeat Yourself).

### FAVOURITE
* **What:** A saved bookmark.
* **Why:** Allows users to build a "wishlist" before actually planning a trip. Also modeled polymorphically so a user can favourite a Destination OR a specific Hotel.

### CONTACT_MESSAGE
* **What:** Submissions from the public "Contact Us" form.
* **Who:** Unregistered site visitors or users.
* **Why:** Modeled as a standalone entity with no relationship to USER. This is because users who have login issues or pre-sales questions need to contact support *without* needing an account.

### NOTIFICATION
* **What:** System alerts (e.g., "Trip starting tomorrow", "Review approved").
* **Why:** Tied directly to the USER to power a real-time bell icon dropdown in the top navigation bar.

---

## 6. System Configuration

### SETTING
* **What:** Key-value pairs for global website configuration (Site Name, Contact Email, Homepage Banner Image).
* **Who:** Modified exclusively by Admins.
* **Why:** Prevents hardcoding variables into the Laravel source code. Admins can update the site's branding directly from the GUI without needing a developer to deploy code changes.
